## 🔍 详细功能差距分析

### 1. 长期记忆系统 ⭐⭐⭐⭐⭐

**V3 已实现**:
- ✅ 5 种记忆类型（User/Feedback/Project/Reference/Knowledge）
- ✅ LLM 驱动的记忆提取（从对话自动抽取）
- ✅ Embedding 向量化（Ollama nomic-embed-text）
- ✅ Qdrant 向量数据库集成
- ✅ 语义搜索（10-50ms，性能提升 1000-10000x）
- ✅ 混合搜索（关键词 + 语义）
- ✅ 自动降级（Qdrant 不可用时降级到 LLM 评分）
- ✅ 相关记忆检索和注入

**V2 现状**:
- ❌ 完全缺失长期记忆功能
- ✅ 有 SQLite 数据库基础（可复用）
- ✅ 有 RAG 系统基础（向量检索能力可迁移）

**实现路径**:
1. **Phase 1**: 基础记忆系统（1-2 天）
   - 数据模型（Memory 结构体）
   - SQLite 存储层
   - CRUD API
   - 基础 CLI 命令

2. **Phase 2**: LLM 驱动提取（1-2 天）
   - `MemoryExtractor` 服务
   - 从对话消息中提取记忆
   - 记忆类型分类

3. **Phase 3**: 向量化和语义搜索（2-3 天）
   - 复用 `agent-rag` 的 Qdrant 客户端
   - 复用 Ollama Embedding
   - 实现向量索引和检索
   - 混合搜索策略

4. **Phase 4**: 集成到对话流程（1 天）
   - `ConversationFlow` 注入相关记忆
   - 自动降级策略
   - CLI 命令完善

**总耗时估算**: 5-8 天

**技术复用**:
- ✅ 可复用 `agent-rag` 的 Qdrant 客户端（80% 代码）
- ✅ 可复用 Ollama Embedding 接口（100% 代码）
- ✅ SQLite 基础设施已有（100% 复用）

---

### 2. 上下文压缩系统 ⭐⭐⭐⭐⭐

**V3 已实现**:
- ✅ 3 种压缩策略
  - Sliding Window（滑动窗口，保留最近 N 条）
  - Semantic（LLM 生成摘要）
  - Hierarchical（分层压缩，适合长对话）
- ✅ 智能策略选择（基于消息数和复杂度）
- ✅ Token 计数（SharpToken = Rust tiktoken-rs）
- ✅ 自动触发（消息数 >= 15）
- ✅ 压缩历史记录

**V2 现状**:
- ❌ 完全缺失上下文压缩功能
- ⚠️ 长对话会导致 Token 超限

**实现路径**:
1. **Phase 1**: Token 计数（1 天）
   - 集成 `tiktoken-rs` crate
   - Token 统计工具

2. **Phase 2**: 滑动窗口策略（1 天）
   - 简单的窗口截断
   - 保留系统消息和最近 N 条

3. **Phase 3**: 语义压缩策略（2 天）
   - LLM 生成摘要
   - 关键信息保留

4. **Phase 4**: 自动触发和集成（1 天）
   - `ConversationFlow` 集成
   - 自动压缩触发
   - 压缩历史记录

**总耗时估算**: 5 天

**技术要点**:
- 需要 `tiktoken-rs` crate（Rust 版 SharpToken）
- LLM 调用已有（复用 `agent-llm`）

---

### 3. 文件上传系统 ⭐⭐⭐⭐

**V3 已实现**:
- ✅ 文件上传/下载/删除
- ✅ 20+ 种文件类型支持
- ✅ 对话中引用（`@file:filename` 语法）
- ✅ 同时引用多个文件
- ✅ 跨会话文件访问
- ✅ 三级权限（Private/Shared/Public）
- ✅ 权限管理（授予/撤销）
- ✅ 版本控制（历史版本、恢复）
- ✅ 11 个 CLI 命令

**V2 现状**:
- ❌ 完全缺失文件上传功能
- ⚠️ 无法处理用户提供的文件

**实现路径**:
1. **Phase 1**: 基础文件存储（2 天）
   - 文件系统存储（`~/.agent-v2/uploads/`）
   - 数据库模型（文件元数据）
   - 上传/列表/删除 API

2. **Phase 2**: 对话引用（1-2 天）
   - `@file:` 语法解析
   - 文件内容读取和注入
   - `ConversationFlow` 集成

3. **Phase 3**: 跨会话和权限（2-3 天）
   - 访问级别（Private/Shared/Public）
   - 权限管理表
   - 权限检查逻辑

4. **Phase 4**: 版本控制（2 天）
   - 版本表设计
   - 版本创建和回滚
   - CLI 命令

**总耗时估算**: 7-10 天

**技术要点**:
- 文件存储：使用 `tokio::fs`
- MIME 类型检测：`mime_guess` crate
- 文件类型：参考 V3 的 20+ 种类型映射

## ⚠️ 风险和挑战

### 技术风险

1. **Rust async 生态差异**
   - V3 用 .NET Task，V2 用 Tokio
   - 需要适配异步模型
   - **缓解**: Tokio 文档完善，社区活跃

2. **依赖 crate 稳定性**
   - `tiktoken-rs` 相对较新
   - `cron` crate 稳定性
   - **缓解**: 选择 star 多、维护活跃的 crate

3. **Qdrant 集成已有（RAG）**
   - ✅ 降低风险
   - 复用现有代码

### 时间风险

1. **估算偏乐观**
   - 实际可能需要 35-40 天
   - **缓解**: 留 20% buffer

2. **测试和调试时间**
   - 集成测试可能需要额外时间
   - **缓解**: 每个功能完成后立即测试

### 资源风险

1. **全职开发假设**
   - 如果非全职，时间翻倍
   - **缓解**: 拆分成小任务，逐步实施
