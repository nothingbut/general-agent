## 概述

V3.1 引入了**智能搜索**和**智能标签**两大核心功能，让会话管理更加高效便捷。这些功能深度集成 LLM，提供语义理解和智能推荐能力。

### 🎯 核心目标

- **提升检索效率** - 使用自然语言快速找到历史会话
- **增强组织能力** - 通过标签系统分类和管理会话
- **智能化体验** - LLM 驱动的查询理解和标签建议

## 智能搜索系统

### 🔍 功能特性

#### 1. 自然语言查询

使用自然语言描述搜索需求，系统会智能理解查询意图。

**示例**:
```bash
/search "上周关于Python的讨论"
/search "最近3天的bug修复"
/search "带有ML标签的会话"
```

**工作原理**:
1. 用户输入自然语言查询
2. `NaturalLanguageQueryService` 使用 LLM 理解查询意图
3. 提取关键词、时间范围、标签过滤条件
4. 生成结构化的 `SearchQuery` 对象
5. 执行数据库查询并返回结果

#### 2. 多字段检索

同时搜索会话的标题、消息内容和标签，提高召回率。

**支持的搜索字段**:
- **标题** - 会话标题的精确匹配或模糊匹配
- **内容** - 消息内容的全文搜索（FTS5）
- **标签** - 按标签名称过滤
- **时间** - 按创建时间或更新时间范围过滤

**查询示例**:
```bash
# 按标题搜索
/search "项目需求"

# 按标签搜索
/search --tag Python --tag ML

# 按时间搜索
/search "上周" --type session

# 组合搜索
/search "Python" --tag bug --after "2026-03-20"
```

#### 3. 时间范围过滤

支持相对时间（如 "上周"）和绝对时间（如 "2026-03-20"）。

**支持的时间格式**:
- **相对时间**: "今天", "昨天", "上周", "最近3天", "本月"
- **绝对时间**: "2026-03-20", "2026-03-20 10:30:00"
- **时间范围**: `--after` 和 `--before` 参数

**时间解析示例**:
```bash
# 相对时间
/search "上周的会话"              # 自动解析为 7 天前至今
/search "最近3天" --type session  # 3 天前至今

# 绝对时间
/search --after "2026-03-20"      # 2026-03-20 之后
/search --before "2026-03-25"     # 2026-03-25 之前

# 时间范围
/search --after "2026-03-20" --before "2026-03-25"
```

#### 4. LRU 查询缓存

常用查询会被缓存，加速响应时间。

**缓存策略**:
- **容量**: 100 个查询
- **淘汰策略**: LRU（Least Recently Used）
- **命中率**: >70%（根据 UAT 测试）
- **缓存键**: 查询文本 + 参数哈希

**性能对比**:
| 场景 | 首次查询 | 缓存命中 | 提升 |
|------|---------|---------|------|
| 简单查询 | ~80ms | ~30ms | 2.7x |
| 复杂查询 | ~150ms | ~50ms | 3x |
| LLM 查询 | ~3000ms | ~50ms | 60x 🚀 |

- 提取关键词和搜索参数

- 超时保护（默认 5 秒）

**SearchService**:
```csharp

```

**功能**:
- 执行数据库查询
- 结果排序和分页
- 相关度评分
- 缓存集成

#### 查询流程

```
用户输入
   ↓
自然语言解析 (NaturalLanguageQueryService)
   ↓
检查缓存 (SearchQueryCache)
   ↓ (未命中)
生成 SearchQuery
   ↓
数据库查询 (SQLite + FTS5)
   ↓
结果排序和评分
   ↓
缓存结果
   ↓
返回结果
```

## 智能标签系统

### 🏷️ 功能特性

#### 1. 自动标签建议

基于会话内容，LLM 智能推荐相关标签。

**示例**:
```bash
You> /tag suggest
✓ 建议以下标签:
  🐍 Python
  🤖 Machine Learning
  📊 Data Analysis
  🔧 Debugging
  📝 Documentation

添加标签? (y/n): y
✓ 已添加 5 个标签
```

**工作原理**:
1. 收集当前会话的所有消息
2. `SmartTagService` 使用 LLM 分析内容
3. LLM 返回 3-5 个推荐标签
4. 用户确认后添加到会话

#### 2. 自定义样式

支持 Emoji 🎨 和十六进制颜色 #FF6347。

**添加带样式的标签**:
```bash
# 基础标签
/tag add Python

# 带 Emoji
/tag add Python --emoji 🐍

# 带颜色
/tag add Python --color #FFD43B

# 完整样式
/tag add Python --emoji 🐍 --color #FFD43B
```

**显示效果**:
```

🤖 ML         #00C7B7  (LLM)
🔧 Debug      #FF6347  (User)
```

#### 3. 批量管理

一次操作管理多个标签。

**批量添加**:

**批量移除**:

**查看标签**:

区分 User、LLM、System 三种标签来源。

**标签来源**:
- **User** - 用户手动添加的标签
- **LLM** - LLM 建议并被接受的标签

### 🗄️ 数据库设计

#### session_tags 表

```sql
CREATE TABLE session_tags (
    id TEXT PRIMARY KEY,                    -- GUID
    session_id TEXT NOT NULL,               -- 会话 ID
    name TEXT NOT NULL,                     -- 标签名称
    emoji TEXT,                             -- Emoji (可选)
    color TEXT,                             -- 颜色 (可选)
    source TEXT NOT NULL,                   -- User | LLM | System
    created_at TIMESTAMP NOT NULL,          -- 创建时间
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE,
    UNIQUE (session_id, name)              -- 同一会话不能有重复标签
);

CREATE INDEX idx_session_tags_session_id ON session_tags(session_id);
CREATE INDEX idx_session_tags_name ON session_tags(name);
CREATE INDEX idx_session_tags_source ON session_tags(source);
```

#### 全文搜索索引 (FTS5)

```sql
-- FTS5 虚拟表
CREATE VIRTUAL TABLE sessions_fts USING fts5(
    session_id UNINDEXED,
    title,
    content,
    tokenize = 'unicode61'
);

-- 触发器: 自动更新 FTS5 索引
CREATE TRIGGER sessions_fts_insert AFTER INSERT ON sessions
BEGIN
    INSERT INTO sessions_fts(session_id, title, content)
    VALUES (NEW.id, NEW.title, '');
END;

CREATE TRIGGER sessions_fts_update AFTER UPDATE ON sessions
BEGIN
    UPDATE sessions_fts SET title = NEW.title WHERE session_id = NEW.id;
END;

CREATE TRIGGER sessions_fts_delete AFTER DELETE ON sessions
BEGIN
    DELETE FROM sessions_fts WHERE session_id = OLD.id;
END;
```

### 🧩 设计决策

#### 1. 为什么选择 LRU 缓存?

**问题**: 频繁的 LLM 调用会导致响应延迟和成本增加。

**决策**: 使用 LRU 缓存存储查询结果。

**理由**:
- **命中率高** - 用户往往会重复相似的查询
- **内存可控** - 固定容量（100 个查询）
- **简单高效** - 淘汰策略清晰，实现简单

**效果**:
- 缓存命中率 >70%（UAT 测试）
- 响应时间从 ~3s 降至 ~50ms（60x 提升）

#### 2. 为什么使用 FTS5 而不是简单的 LIKE 查询?

**问题**: `LIKE '%keyword%'` 查询性能差，无法支持复杂搜索。

**决策**: 使用 SQLite FTS5 全文搜索引擎。

**理由**:
- **性能优势** - FTS5 使用倒排索引，查询速度快
- **功能丰富** - 支持多字段搜索、近似匹配、词干提取
- **易于集成** - SQLite 内置，无需额外依赖

**效果**:
- 搜索响应时间 <100ms
- 支持复杂查询（如 `title:Python OR content:debugging`）

#### 3. 为什么标签建议只返回 3-5 个标签?

**问题**: 返回太多标签会让用户难以选择，返回太少又可能遗漏重要信息。

**决策**: 返回 3-5 个标签，并按相关性排序。

**理由**:
- **认知负荷** - 研究表明人类短期记忆容量约为 5±2 个项目
- **实用性** - 3-5 个标签足以覆盖会话的主要主题
- **可扩展性** - 用户可以手动添加更多标签

**效果**:
- 用户满意度高（UAT 反馈）
- 标签建议准确率 >80%

#### 4. 为什么区分标签来源 (User/LLM/System)?

**问题**: 无法追溯标签的添加方式，难以评估 LLM 的建议质量。

**决策**: 为每个标签添加 `source` 字段。

**理由**:
- **可追溯性** - 知道哪些标签是 LLM 建议的，哪些是用户手动添加的
- **质量评估** - 可以统计 LLM 建议的接受率
- **未来优化** - 可以基于用户行为优化 LLM 提示词

**效果**:
- 可以生成标签来源报告
- 为未来的 LLM 优化提供数据支持

## 已知限制

### ⚠️ 搜索功能限制

#### 1. FTS5 查询逻辑未完整实现

**现状**: 当前 `SearchService.SearchWithNaturalLanguageAsync` 返回空结果。

**原因**: FTS5 查询逻辑未完整实现（时间限制）。

**影响**: 搜索命令可用但无实际结果。

**临时方案**: 使用 `/list` 命令浏览会话列表。

**计划**: 在 V3.2 中完善 FTS5 查询逻辑。

#### 2. 搜索结果无分页 UI

**现状**: 搜索结果支持分页参数，但 CLI 没有分页导航 UI。

**影响**: 结果过多时需要手动指定 `--page` 参数。

**计划**: 在 V3.2 中添加交互式分页 UI（如 `[1] [2] [3] > [Next]`）。

### ⚠️ 标签功能限制

#### 1. LLM 超时策略固定

**现状**: 标签建议的 LLM 调用超时固定为 5 秒。

**影响**: 在网络不稳定时可能超时失败。

**计划**: 在 V3.2 中添加可配置的超时参数。

#### 2. 标签重命名不支持

**现状**: 无法重命名已添加的标签。

**影响**: 发现标签名称不合适时需要删除并重新添加。

**计划**: 在 V3.2 中添加 `/tag rename` 命令。

### ⚠️ 性能限制

#### 1. 缓存容量固定

**现状**: 查询缓存容量固定为 100 个查询。

**影响**: 在高频使用场景下可能命中率下降。

**计划**: 在 V3.2 中添加可配置的缓存容量参数。

#### 2. 标签建议消息数量固定

**现状**: 标签建议固定分析最近 20 条消息。

**影响**: 对于长会话可能遗漏重要信息。

**计划**: 在 V3.2 中添加可配置的消息数量参数。
